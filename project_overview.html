FishEye8K · YOLO11n · ONNX CPU

Efficient Detection

Train a small object detector on fisheye traffic footage, prune it, export it to ONNX, and run it fast on a plain CPU. The project also ships a native C++ runtime that is measured against the Python path on the same model and the same images.

What it does

Five traffic classes

bus (0), bike (1), car (2), pedestrian (3), truck (4). COCO and YOLO inputs are mapped to this fixed order, with camera-aware splits and duplicate checks.

Small model, CPU first

YOLO11n at 640 px, FP32 ONNX. Roughly 2.6 M parameters and a 10 MiB file, so it fits an edge box with no GPU.

Physical pruning, no recovery

Channels are removed at 10% and 20% targets and the pruned checkpoint is validated as-is. There is no fine-tuning, no INT8, no distillation stage.

Two independent runtimes

Python inference and a native C++ executable with reusable tensors. They are checked against each other instead of sharing code, so parity means something.

Stage 1

Prepare labels

yolo/prepare_yolo.py

In COCO JSON, or a YOLO image folder plus one .txt per image

Out images/{train,val}, labels/, annotations/{train,val}.json, manifest.json, data.yaml

  • Every source category is remapped onto the fixed order bus, bike, car, pedestrian, truck. A custom COCO mapping goes through --category-map.
  • Split by camera, parsed from camera<id>_<M|A|E|N>_ in the filename, so no scene appears in both splits. --split random is the fallback when names carry no camera ID.
  • Byte-identical images across splits are rejected by SHA-256. Duplicates inside one split are kept and counted.
  • A validation or test argument without its matching pair is rejected instead of silently ignored. Crowd boxes stay for evaluation; non-crowd ignore=1 regions are rejected because the trainer would learn them as positives.
  • --mode symlink by default, copy for a portable dataset.
Stage 2

Optional D-FINE pseudo labels

yolo/generate_pseudo_labels.py

In unlabeled images, a D-FINE-S/M/L/X checkpoint, --confidence (0.5)

Out extra label files merged into the prepared split

  • Accepts an 80-class or a 5-class checkpoint. Boxes are mapped into the project classes; anything outside the five is dropped.
  • Only unlabeled images are annotated. Held-out validation cameras are excluded, so pseudo labels cannot leak into the measured split.
  • Human labels always win and the merge is idempotent: re-running does not duplicate a pseudo box.
  • Skip this stage entirely if you already have enough labeled data.
Stage 3

Train or resume YOLO11n

yolo/train_yolo.py

In prepared data.yaml, yolo11n.pt COCO weights

Out runs/baseline/weights/best.pt, results.csv, per-epoch validation

  • Defaults: 640 px, 30 epochs, seed 0, deterministic, 2 workers. AMP is off unless you pass --amp.
  • data.yaml is checked first: class names and order must match the project convention.
  • A pruned checkpoint is refused here. Pruning is one-way in this project, so a pruned model cannot re-enter training.
  • --resume restores optimizer, scheduler, scaler, EMA and RNG state, not just weights.
  • The recorded Kaggle run used 15 epochs and batch 32 on a Tesla T4: 0.863 h, 10.2 GB per epoch, best epoch 14.
Stage 4

Prune channels

yolo/prune_yolo.py

In best.pt, the same data.yaml, --prune-ratio (0.1)

Out pruned.pt and pruning.json

  • Torch-Pruning groups find channels that can only be removed together. Channels are then deleted physically, not masked, and rounded to --round-to 8.
  • Every candidate starts from the same baseline. 10% and 20% are separate models, never a chain.
  • Zero optimizer steps: no recovery fine-tuning, no distillation, no INT8. The reported accuracy is what the pruned weights score as-is.
  • The report records per-layer channels before and after, the removed indices and the parameter reduction.
Stage 5

Export FP32 ONNX

yolo/export_yolo.py

In a checkpoint, --image-size (512, 640 or 960), an optional real test image

Out model.onnx plus model.json

  • Static batch-1 [1,3,S,S] FP32 input, opset 17, postprocessing folded in, so the output is raw [1,9,N].
  • Output is compared against PyTorch on random input and on the real image before the export is accepted.
  • The sidecar carries model family, class order, precision, image size, parameter count, ONNX SHA-256 and how many samples were verified.
  • The runtime refuses to load an ONNX file that does not match its sidecar, so a stale pair cannot be measured by accident.
Stage 6

Benchmark, evaluate, compare

yolo/benchmark_yolo.py · yolo/evaluate_yolo.py · yolo/compare_cpp.py

In exported ONNX models, prepared split or the original test JSON

Out summary.json, per-image and per-class CSV, report.md, selection.json

  • Each measurement runs in an isolated process: 20 warm-up passes, 100 repeats, 3 trials, threads 1/2/4. AP is computed at confidence 0.001 with multi-label so the whole precision-recall curve survives.
  • Selection keeps the lowest pipeline p95 within 2 AP points of the baseline. The test split is scored once, with --selected, so the choice is not made on the test data.
  • evaluate_yolo.py scores every image in the original COCO test JSON: AP, fixed-threshold precision/recall/F1, TP/(TP+FP+FN), latency percentiles and RSS.
  • compare_cpp.py runs Python, C++ fresh buffers and C++ reused buffers over the same images in rotating order and fails the run on any input-tensor, raw-output, box or score difference.
Stage 7

Package for a CPU machine

yolo/package_local.py · Dockerfile

In a model folder, optional prepared data.yaml

Out yolo_local.zip, or a Docker image

  • The zip holds the inference runtime, the ONNX files with their sidecars, real copies of the validation images, the two requirements files and LOCAL.md. No torch, no training code.
  • Bundle paths are an allowlist, so a module that is not needed for inference never ships.
  • The Docker image is python:3.11.14-slim-bookworm with evaluate_yolo as the entrypoint. The dataset is mounted read-only at /data.

Native C++ runtime — detailed walkthrough

Everything lives in one file: cpp/src/main.cpp, 448 lines of C++17 with no framework. It builds one executable, build/cpp/efficient_infer, which reads a JSON config, runs a static YOLO11 ONNX model over a list of images and writes JSON reports. It does no drawing, no COCO AP computation and no training.

Dependencies and why they are pinned

cpp/dependencies.lock.json records a URL and a SHA-256 for every downloaded file. cpp/build.py downloads only what is missing or corrupt and aborts on any checksum mismatch. No system packages are installed; CMake and Ninja come from the venv.

Build pipeline

python -m pip install -r requirements/cpp.txt
python cpp/build.py              # first run: fetch + verify headers, symlink ORT, build
python cpp/build.py --offline    # cached dependencies only
  1. Refuses to run unless the platform is Linux and onnxruntime.__version__ == "1.31.0".
  2. Downloads pinned headers into third_party/cpp/ and verifies SHA-256.
  3. Symlinks libonnxruntime.so, .so.1, .so.1.31.0 and the providers library from the installed Python package into third_party/cpp/lib/.
  4. Runs the CMake preset release: Ninja generator, CMAKE_BUILD_TYPE=Release, C++17.
  5. Compiles with -Wall -Wextra -Wpedantic -fno-fast-math -ffp-contract=off. Disabling fast-math and FP contraction is deliberate: it keeps float results reproducible and comparable with Python.
  6. Writes build/cpp/build_info.json with the ORT version, library path and hash, main.cpp hash and the lock-file hash.

CMakeLists.txt links the ORT library with an RPATH to third_party/cpp/lib, so the binary finds the shared library without LD_LIBRARY_PATH.

Program flow

  1. Argument check. Only --config <file> is accepted; anything else prints usage and exits 2.
  2. Config resolution. Every relative path is joined with project_root, which is itself relative to the config file. Moving the config does not silently change what it points at.
  3. Output guard. The output directory must be empty, and must not be inside the image directory. A second run cannot overwrite or pollute a previous report.
  4. Range validation. Threads ≥ 1, warmup ≥ 0, repeats ≥ 1, finite confidence and NMS IoU in [0, 1], buffer mode fresh or reuse, max_detections ≥ 1.
  5. Model identity check. Reads <model>.json and requires the class list to equal bus/bike/car/pedestrian/truck, model_family == "yolo11", precision == "float32", and onnx_sha256 to equal the real hash of the model file. A swapped or edited model fails before any inference.
  6. Image list. From a manifest JSON, from COCO annotations (only the images records are used, ground truth is ignored), or by recursively scanning the image directory for png/jpg/jpeg/bmp and sorting names. Paths are rejected if absolute or containing ...
  7. Session setup. Asserts ONNX Runtime 1.31.0, sets intra-op threads from config, inter-op to 1, ORT_ENABLE_ALL graph optimization, then validates the graph signature is exactly static FP32 [1,3,S,S] → [1,9,N]. Anything else is refused rather than guessed at.
  8. Warm-up. Runs warmup predictions over the list cyclically, untimed, so allocator and ORT caches are warm before measurement.
  9. Measured loop. Per image: decode, check dimensions against the manifest when present, predict, record stage timings. Predictions are written once, from repeat 0, even when repeats > 1.
  10. Aggregation and output. Mean/p50/p95/p99 per stage, FPS as 1000/mean, peak RSS from getrusage, then per_image.json, predictions.json, summary.json and the effective config.json.

Preprocessing: Pillow-compatible letterbox

The goal is not "a resize", it is the same pixels Pillow produces, so the two backends can be compared fairly.

  • Resize plan caching. A ResizePlan is computed once per source (width, height) pair and stored in a map. It holds the target size, padding offsets, scale ratio and two separable filter kernels.
  • Dimensions. ratio = min(size/w, size/h), then target dimensions use nearbyint (ties-to-even) to match Python's round.
  • Padding offsets. Centered with the same -0.1 bias Pillow applies, so the odd-size case lands on the same pixel.
  • Bilinear kernel. Weights are normalized per output pixel and stored as 22-bit fixed-point integers (1 << 22). Each accumulator starts at 1 << 21 for round-half-up, and the result is shifted by 22 and clamped to 0–255.
  • Two passes. Horizontal resize into a scratch buffer, then vertical resize into the final buffer, skipping a pass when the axis already matches. Integer math keeps it deterministic and fast.
  • Tensor fill. The CHW float buffer is filled with 114/255 padding, then the resized HWC RGB bytes are scattered into their planes as value / 255.

Postprocessing: decode, restore, NMS

The export is transposed: 9 channels by N anchors, laid out [1,9,N]. Channels 0–3 are cx, cy, w, h; channels 4–8 are the five class scores.

  1. Finiteness gate. All nine values for an anchor must be finite; otherwise the anchor is skipped. NaN can never become a detection.
  2. Class and score. The label starts at class 0 with channel 4 as its score, then channels 5–8 compete; highest wins. Below confidence, the anchor is dropped.
  3. Coordinate restoration. cxcywh becomes xyxy, padding offsets are subtracted, the result is divided by the letterbox ratio and clamped to the original image bounds. Degenerate boxes are discarded.
  4. Candidate ordering. Sorted by score descending, ties broken by anchor index, then capped at 30,000 candidates.
  5. Class-aware greedy NMS. Each of the five classes is filtered separately against already-kept boxes of that class; a box is suppressed when IoU exceeds nms_iou.
  6. Final order. A stable sort by score descending, ties by class then anchor, matching Python. The list is truncated to max_detections (default 300).

Both modes report input_tensor_allocations and output_tensor_allocations in summary.json, counted including warm-up. In the measured 100-image run, reuse created one of each while fresh created 120 per trial. Those counters cover application tensor creation only — not decoder buffers and not ONNX Runtime internals.

Reuse requires static graph shapes, which this export guarantees. Resize plans and the candidate/NMS vectors also keep their capacity across images.

Correctness gates in the comparison

yolo/compare_cpp.py runs Python, cpp_fresh and cpp_reuse as separate processes, in rotating order across trials, on the same seeded image subset and the same model. It fails the run rather than reporting a speedup when:

  • input tensors are not exactly equal;
  • raw outputs differ beyond atol=1e-4, rtol=1e-5;
  • detection counts or classes differ, or matching is not a complete one-to-one assignment;
  • box error exceeds 0.01 px or score error exceeds 1e-5;
  • any non-finite value appears.

Matching is order-independent and handles equal-score overlapping candidates, so a valid correspondence cannot fail merely because the sort order changed.

Deliberate limits

  • Static shapes only. The graph must be a fixed [1,3,S,S] → [1,9,N]. Dynamic axes, batching and variable input sizes are rejected, not supported partially.
  • CPU, FP32, batch 1. No CUDA, no TensorRT, no INT8, no batching.
  • JPEG may differ from Pillow. stb_image is a different decoder. PNG is verified to match; a JPEG speed comparison only counts after the parity gate passes.
  • JSON only. No annotated images and no AP: the CLI writes predictions for an external evaluator.
  • Not in the Docker image. The provided Dockerfile packages the Python runner. Relocating the binary requires its ORT shared library and the license notices in cpp/THIRD_PARTY.md.
  • Config keys are strict where it matters. An unknown model family, wrong class order, wrong precision or a checksum mismatch is a hard error.

Tests

python -m pytest tests/test_cpp_runtime.py -q runs the compiled executable and covers PNG input-tensor parity for odd, non-square, upsampled, downsampled and one-pixel images, same-class NMS and cross-class overlap, invalid anchors, coordinate restoration, model checksum validation, and allocation counts in both buffer modes. Without a built binary these tests are skipped, not failed.

How to run

Install

python -m pip install -r requirements/training.txt   # training + project imports
python -m pip install -r requirements/inference.txt  # CPU inference only
python -m pip install -r requirements/benchmark.txt  # benchmarking
python -m pip install -r requirements/cpp.txt        # native build deps

Prepare and train (Kaggle GPU)

python yolo/prepare_yolo.py --format yolo \
  --images /kaggle/input/fisheye/images/train \
  --labels /kaggle/input/fisheye/labels/train \
  --val-images /kaggle/input/fisheye/images/val \
  --val-labels /kaggle/input/fisheye/labels/val \
  --output /kaggle/working/yolo_workflow/prepared

python yolo/train_yolo.py --help
python yolo/prune_yolo.py --help
python yolo/export_yolo.py --help
python yolo/package_local.py --help

Infer and evaluate (local CPU)

python yolo/infer_yolo.py --model models/baseline_640.onnx --source path/to/image.jpg
python yolo/benchmark_yolo.py --help
python yolo/evaluate_yolo.py --help

Native C++ runtime

python cpp/build.py --preset release
# then run the preset in configs/cpp_cpu.json against your dataset
python yolo/compare_cpp.py --help

Tests

python -m pytest tests -q

Honest limits

Small objects are the weak spot. AP small is 6.72% and pedestrian AP50:95 is 4.83%. The 640 px fisheye view shrinks distant people to a few pixels. Higher export resolutions (960) exist for this reason.
No accuracy recovery after pruning. Pruned checkpoints are validated directly. If the 20% target costs too much AP, nothing here wins it back — recovery training or distillation would have to be added.
The C++ speedup is modest and partly unattributed. Per-trial means varied by up to 14 ms, and C++ also changes preprocessing, NMS and the JPEG decoder. The 1.26× is a measured ratio on one machine, not a proven allocation-only win.
Results come from one hardware profile. All latency numbers are Intel i7-1360P, 4 threads. They say nothing about Qualcomm or ARM targets.
